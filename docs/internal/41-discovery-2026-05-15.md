# 4.1 Workflow Execution Discovery
**Version:** 1.0
**Date:** 2026-05-15
**Milestone:** MS-006 — 4.1 Discovery complete
**Joint with:** EP-021 (planning workflow gaps catalogued in §5)

---

## 1. Scope and method

This document catalogues execution workflow gaps, step-skip patterns, and quality failure patterns as they exist in SweetClaude v4.0.7-beta. Sources: live backlog stories (STORY-013, 015, 018, 019, 020), the April 2026 workflow caucus (`caucus_review_workflow_catalog.md`), and direct inspection of `config/workflow-templates.yaml`, `phase-gates.md`, and the skills that run during execution phases (`go`, `code-feature`, `code-debt`, `code-verify`, `code-review`, `code-tdd`).

## 2. Confirmed workflow taxonomy for 4.1

The target for MS-007 is 15 workflow types — 12 execution, 3 planning. These are confirmed from `workflow-templates.yaml` and `phase-gates.md`:

### 2.1 Execution workflows (12)

| Work type | Phase sequence | Current skill coverage |
|---|---|---|
| `net-new-feature` | DISCOVER → DEFINE → DESIGN → PLAN → IMPLEMENT → VERIFY → SHIP | Partial — DISCOVER/DEFINE/DESIGN phases not enforced in `code-feature` |
| `enhancement` | DEFINE → DESIGN → IMPLEMENT → VERIFY → SHIP | DESIGN gate not enforced; `code-feature` skips to IMPLEMENT |
| `tech-debt` | DEFINE → SCOPE → IMPLEMENT → VERIFY → SHIP | SCOPE phase (lock behavior with tests) not enforced in `code-debt` |
| `external-integration` | DISCOVER → DEFINE → DESIGN → PLAN → IMPLEMENT → VERIFY → SHIP | No dedicated skill; treated as `net-new-feature` |
| `bug-fix` | DIAGNOSE → IMPLEMENT → VERIFY → SHIP | `code-issue` partially implements; DIAGNOSE phase not gated |
| `hotfix` | DIAGNOSE → IMPLEMENT → SHIP → POST-MORTEM | `something-broke` exists but POST-MORTEM spawn is not enforced |
| `security-patch` | DIAGNOSE → IMPLEMENT → VERIFY → SHIP | VERIFY hard gate (mandatory security review) not enforced by any skill |
| `performance-optimization` | DIAGNOSE → DESIGN → IMPLEMENT → VERIFY → SHIP | No dedicated skill |
| `infrastructure-change` | DEFINE → DESIGN → IMPLEMENT → VERIFY → SHIP | DESIGN hard gate (solutioning gate at GA+) advisory only |
| `compliance-requirement` | ASSESS → DEFINE → DESIGN → IMPLEMENT → VERIFY → SHIP | No dedicated skill |
| `technology-migration` | ASSESS → DESIGN → PLAN → IMPLEMENT → VERIFY → CUTOVER → CLEANUP | Migration runner exists; CUTOVER hard gate (human decision) not enforced |
| `data-migration` | ASSESS → DESIGN → PLAN → IMPLEMENT → VERIFY → SHIP | VERIFY hard gate (integrity checks) not enforced |

### 2.2 Planning workflows (3)

Treated separately — see §5 (joint EP-021 findings).

| Work type | Phase sequence |
|---|---|
| `course-correction` | DISCOVER → DEFINE → TRIAGE → SHIP |
| `security-planning` | DISCOVER → DEFINE → SHIP |
| `release-planning` | DEFINE → PLAN → SHIP |

### 2.3 Out-of-scope for 4.1 taxonomy

These types appear in `workflow-templates.yaml` but are not part of the 15-type target: `sprint-planning`, `backlog-management`, `user-feedback-triage`, `onboarding-flow-design`, `api-deprecation`, `rollback-revert`. They remain in the templates as supporting types but are not subject to enforcement in 4.1.

## 3. Step-skip patterns

### 3.1 Work type is never selected

**Gap:** No skill currently asks "what type of work is this?" before starting. `go` routes to an active story and enters `code-feature` regardless of whether the story is a net-new-feature, an enhancement, a bug-fix, or a tech-debt item. The work type field does not exist in story frontmatter.

**Consequence:** The wrong phase sequence is silently applied to every story. A `tech-debt` item missing the SCOPE phase ships without locked behavior tests. A `hotfix` that should follow the compressed shape goes through `code-feature` as if it were an enhancement.

**Fix required by:** STORY-020 (upfront assessment adds `work_type` to frontmatter and selects the correct template).

### 3.2 DESIGN phase skip on enhancements

**Gap:** `code-feature` does not check for DESIGN phase completion before entering IMPLEMENT. For `enhancement` work type, DESIGN (approach decision, contract review, edge cases) is a defined phase but nothing blocks progression without it.

**Frequency:** High — most enhancement-type stories go directly from DEFINE (acceptance criteria written) to IMPLEMENT.

**Impact:** Discovered design flaws surface in VERIFY rather than DESIGN, where they cost more to fix.

### 3.3 SCOPE phase skip on tech-debt

**Gap:** `code-debt` does not enforce the SCOPE phase. SCOPE requires locking existing behavior with tests that would fail on any behavior change, then verifying those tests fail on a deliberate break before implementation begins. Currently `code-debt` presents advice but does not block.

**Impact:** Refactors ship without a confirmed behavioral safety net. The "refactor didn't change behavior" claim cannot be verified.

### 3.4 DIAGNOSE phase skip on bug-fix

**Gap:** `code-issue` prompts for root cause analysis but does not gate IMPLEMENT on a written reproduction case. A developer who already knows the fix can skip to implementation without ever documenting what the root cause was or confirming the reproduction case.

**Impact:** Fixes target symptoms rather than root causes. The missing test that should have caught the bug is never identified.

### 3.5 POST-MORTEM spawn not enforced after hotfix

**Gap:** `phase-gates.md` marks POST-MORTEM as required (not optional) after `hotfix` SHIP. No skill currently spawns or flags a POST-MORTEM work item after a hotfix completes.

**Impact:** Post-incident analysis doesn't happen. Recurrence prevention is not built into the workflow.

### 3.6 CUTOVER hard gate is advisory

**Gap:** The `technology-migration` work type has a hard gate at CUTOVER requiring an explicit human decision logged to the decision log. The migration runner (`scripts/migrations/runner.py`) performs the cutover mechanics but does not enforce a pre-cutover decision gate.

**Impact:** Migrations cut over without explicit confirmation that cutover criteria are met.

## 4. Quality failure patterns

### 4.1 No breaking-change flag → no adversarial review trigger

**Gap:** Story frontmatter has no `breaking` field. Without it, nothing can detect that a story changes public API, breaks backward compatibility, or has a blast radius beyond an isolated module.

**Consequence:** Breaking changes receive the same review process as isolated bug fixes. The adversarial code-reviewer pass (structurally separated from author context) never fires. STORY-019 documents a concrete incident: BUG-007 shipped because author and test-writer shared the same blind spot.

**Fix required by:** STORY-019 (adds `breaking` field and mandatory adversarial pass for `breaking: true` stories).

### 4.2 Caucus composition has no role enforcement

**Gap:** When a caucus runs, the composition (which agents, in what roles) is not validated. There is no check that the adversarial slot is filled. A caucus can consist entirely of agents inclined to agree with the author.

**Consequence:** Caucus outputs optimize for author confidence rather than finding what the author missed. Per the April 2026 workflow caucus: "a caucus where every agent agrees with the author is useless."

**Fix required by:** STORY-020 (templates specify caucus composition by role: adversarial / continuity / domain-expert; adversarial slot is mandatory for `breaking: true`).

### 4.3 TDD level selection is undocumented and inconsistent

**Gap:** TDD level (0–3) is chosen per-story without a documented rationale. The selection is not recorded in the story file, not tied to `work_type` or `breaking` status, and not auditable after the fact.

**Consequence:** Level 0 or 1 is chosen for stories that should be Level 2+ (breaking changes, external-input parsing, complex state transitions). The resulting test suites look comprehensive by count but lack adversarial coverage.

**Fix required by:** STORY-020 (assessment maps work type + complexity + breaking status to a minimum TDD level; override requires logged rationale).

### 4.4 Status state machine violations in skills

**Gap:** `planning-concepts.md` defines the valid status vocabulary: `new → active → done` (primary path), plus `blocked`, `paused`, `cancelled`. The status `in_progress` is not a valid state. Several skills still use `in_progress` internally or allow it in frontmatter without rejection.

**Consequence:** Stories enter states not recognized by the model. Queries that depend on status (big-picture, go, project-issues) produce inconsistent results.

**Fix required by:** STORY-015 (enforce the state machine in every skill that reads or writes story status).

### 4.5 Phase gate exit criteria are defined but not checked

**Gap:** `phase-gates.md` defines entry and exit criteria for every phase. No skill currently reads `phase-gates.md` and checks exit criteria before allowing phase advancement. A story moves from DESIGN to PLAN, or IMPLEMENT to VERIFY, on user say-so only — the gate criteria are advisory.

**Consequence:** Stories advance through phases with incomplete artifacts. A story entering IMPLEMENT without a written architecture doc or tech spec is structurally indistinguishable from one that completed DESIGN properly.

**Fix required by:** MS-009 (design consensus on gate enforcement model) → MS-010 (technical spec on how gates are checked in skills).

### 4.6 No per-phase status on stories

**Gap:** Story frontmatter has a single `status` field that tracks the overall story lifecycle. There is no record of which phase the story is currently in, what is blocking it in that phase, or which artifact is the primary workfile for the current phase.

**Consequence:** Resuming a story after a break requires reading the body to reconstruct context. `go` cannot tell the user "you were in DESIGN, the tech spec is at X."

**Fix required by:** STORY-018 (per-phase status table as a frontmatter or body section on every story).

## 5. Planning workflow gaps (EP-021 joint findings)

The 3 planning workflow types have lighter skill coverage than execution types. These gaps feed MS-026 (4.3 planning workflow types defined).

### 5.1 Course-correction

`workflow-templates.yaml` defines the sequence: DISCOVER → DEFINE → TRIAGE → SHIP. No dedicated skill routes through this sequence. A course-correction today is handled through a combination of ad-hoc conversation and manual backlog edits — the TRIAGE phase (review in-flight work: keep / drop / repurpose / defer) is documented in `phase-gates.md` but has no skill support.

**Gap for 4.3:** Need a `sweetclaude:course-correction` skill that:
- Prompts for the signal that triggered the correction and confirms it's a pattern, not a one-off
- Runs TRIAGE as a structured review of every in-flight item
- Produces a revised direction document
- Commits the corrected state to backlog

### 5.2 Security planning

`workflow-templates.yaml` defines: DISCOVER → DEFINE → SHIP. The `testing-security` skill exists but addresses security testing, not security roadmap planning. No skill runs the full security-planning workflow (business model interview, regulatory mapping, phased roadmap, quick-wins backlog).

**Gap for 4.3:** The security-planning workflow currently lives only in `phase-gates.md` prose. A skill routing through the defined phases is needed.

### 5.3 Release planning

`workflow-templates.yaml` defines: DEFINE → PLAN → SHIP. The `deploy-ship` skill handles SHIP mechanics but not PLAN (changelog drafting, pre-release checklist assembly, migration guide authorship, rollback verification). Release planning is currently fully manual.

**Gap for 4.3:** The PLAN phase of a release (everything that happens before SHIP) has no skill support. This produces inconsistent release artifacts — changelogs that miss items, migration guides that are late.

### 5.4 Sprint-planning and backlog-management

These are supporting workflow types, not primary execution types, but they have recurring gap patterns observed across sessions:

- `project-backlog-triage` exists but does not enforce a priority ordering protocol
- Sprint commitments are made without WIP checks (relevant to Kanban mode enforcement — STORY-013)
- There is no workflow for "user-feedback triage → backlog item creation" that preserves the signal source on the resulting story
