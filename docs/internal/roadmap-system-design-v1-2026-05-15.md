**Date:** 2026-05-15
**Status:** Draft
**Branch:** experimental/roadmap-cache-v1
**Drives:** STORY-011, STORY-012, go routing, big-picture rendering
**Design decisions referenced:** DEC-24, DEC-25, DEC-26, DEC-29

---

## 1. Core architecture

**Markdown files are the source of truth.** Per-item files with YAML frontmatter, stored in git, human-readable, diffable, mergeable across collaborators.

**A gitignored SQLite cache provides fast queries.** Built on session start by scanning all markdown files and parsing frontmatter. Skills read from the cache. Writes go to markdown files, then refresh the cache.

**No shared files.** INDEX.md is eliminated. Relationship lists on parent entities (`stories: []`, `epics: []`) are eliminated. Counters are eliminated. Relationships are expressed through reference fields on child entities: stories point to their epic, epics point to their release. The cache materializes these into queryable relationships.

**Session state is per-developer.** `.sweetclaude/state/` is gitignored. `active_work_item`, `active_epic`, and other session-scoped fields are local — two developers on the same repo never conflict on session state.

### Why this architecture

Teams of 2-3 are already using SweetClaude. The merge conflict sources today are all shared files:
- INDEX.md — every story create/close touches it
- Milestone/epic `stories: []` lists — multiple developers updating the same list
- Counters — both incrementing the same number

Eliminating shared files means per-item operations are per-file, which git merges naturally. SQLite as source of truth was considered and rejected — binary files cannot three-way merge.

## 2. Hierarchy

```
Release → Epic (with Objective + Completion Criteria) → Stories
```

- **Release** — a version cut (e.g., 4.1). Epics declare which release they belong to.
- **Epic** — a capability area (e.g., Workflow Engine). Has one objective and N completion criteria. Stories declare which epic they belong to and their sequence within it.
- **Story** — a work item. Declares its epic and sequence position.

Only one epic may have `status: active` at a time. Stories within the active epic are worked in `epic_sequence` order.

If a story needs work but belongs to a different epic (or no epic), it is moved to the active epic rather than worked in isolation.

## 3. Mode-gated behavior

| Mode | Roadmap present? | go Priority 3 | Notes |
|---|---|---|---|
| **flow** | No | Skipped | Passive posture. No releases, no epics. If user wants structure, recommend kanban or another mode. |
| **kanban** | Yes | Active epic routing | One active epic, stories flow through in sequence. |
| **shape_up** | Yes | Active epic routing | Betting table gates which epic becomes active. |
| **agile** | Yes | Active epic routing | Active epic + active sprint. |
| **unset** | No | Skipped | Treated as flow. |

## 5. Entity schemas

### Story (revised frontmatter)

```yaml
---
id: STORY-011
type: story
title: "Roadmap system"
status: new | in_progress | done | deferred | abandoned
priority: now | sooner | soon | later | someday
effort: xs | s | m | l | xl
epic: EP-002          # reference to parent epic (null if unassigned)
epic_sequence: 1      # position within the epic's execution order (null if unassigned)
tags: [roadmap, v4-phase2]
origin: manual
created: 2026-05-15
updated: 2026-05-15
closed_date: null
---
```

Changes from current schema:
- `epic` field already exists — no change
- `epic_sequence` added — integer, determines execution order within the epic
- `milestone` field removed — milestones are now completion criteria on epics
- `sprint` field retained — used in agile mode
- `priority` field retained — used for backlog ordering when no epic is active

### Epic

```yaml
---
id: EP-001
type: epic
title: "Workflow Engine"
status: new | active | done | paused
release: REL-001
objective: "Workflow state tracking, gate enforcement, and session continuity for all 12 execution workflow types."
completion_criteria:
  - "Workflow taxonomy finalized"
  - "State model designed"
  - "Design consensus reached"
  - "Technical spec approved"
  - "Workflow state infrastructure implemented"
  - "All 12 execution workflow types implemented"
  - "Code and security review complete"
  - "Behavioral regression suite passing"
  - "Docs and changelog updated"
depends_on: []
created: 2026-05-15
updated: 2026-05-15
---

## Description
(capability description, context, design references)
```

Key points:
- No `stories: []` list. The epic's stories are derived by querying all stories where `epic: EP-001`, ordered by `epic_sequence`.
- No `epics: []` on releases. A release's epics are derived by querying all epics where `release: REL-001`.
- `completion_criteria` are simple strings. No prioritization or dependencies between them. Marked done manually via the `sweetclaude:epics` skill (stored as a `completion_criteria_done: [0, 2, 4]` index list or similar — design TBD in STORY-012).
- `depends_on` references other epics for cross-epic sequencing.

### Release

```yaml
---
id: REL-001
type: release
title: "v4.1"
status: planning | active | released | abandoned
version: "4.1"
created: 2026-05-15
updated: 2026-05-15
---

## Release notes
(populated at release time)
```

Key points:
- No `epics: []` list. Derived from epic files where `release: REL-001`.
- Minimal schema. Release is primarily a grouping/versioning entity.

## 6. SQLite cache

### Location

```
.sweetclaude/cache/roadmap.db
```

Gitignored. Rebuilt from source files on every session start and after any write operation.

### Schema

```sql
CREATE TABLE items (
  id TEXT PRIMARY KEY,
  type TEXT NOT NULL,          -- story, bug, chore, debt, epic, release
  title TEXT NOT NULL,
  status TEXT NOT NULL DEFAULT 'new',
  priority TEXT,
  effort TEXT,
  epic TEXT,                   -- parent epic ID (stories)
  epic_sequence INTEGER,       -- order within epic (stories)
  release TEXT,                -- parent release ID (epics)
  objective TEXT,              -- epics only
  source_path TEXT NOT NULL,   -- path to the markdown file
  created TEXT,
  updated TEXT,
  closed_date TEXT
);

CREATE TABLE completion_criteria (
  epic_id TEXT NOT NULL,
  seq INTEGER NOT NULL,        -- order within the epic
  criterion TEXT NOT NULL,
  done INTEGER DEFAULT 0,
  PRIMARY KEY (epic_id, seq),
  FOREIGN KEY (epic_id) REFERENCES items(id)
);

CREATE TABLE epic_dependencies (
  epic_id TEXT NOT NULL,
  depends_on TEXT NOT NULL,
  PRIMARY KEY (epic_id, depends_on),
  FOREIGN KEY (epic_id) REFERENCES items(id)
);

CREATE TABLE tags (
  item_id TEXT NOT NULL,
  tag TEXT NOT NULL,
  FOREIGN KEY (item_id) REFERENCES items(id)
);

-- Indexes for common queries
CREATE INDEX idx_items_type ON items(type);
CREATE INDEX idx_items_status ON items(status);
CREATE INDEX idx_items_epic ON items(epic);
CREATE INDEX idx_items_release ON items(release);
CREATE INDEX idx_items_priority ON items(priority);
```

### Lifecycle

1. **Build** — on session start (in `session-preflight.sh` or first skill invocation), scan all markdown files under `docs/product/backlog/` and `docs/product/roadmap/`, parse YAML frontmatter, populate the cache.

2. **Refresh** — after any skill writes to a markdown file, refresh the affected rows. Full rebuild is fast enough (< 100 files) that incremental refresh may not be necessary initially.

3. **Invalidate** — after `git pull`, `git merge`, `git checkout`, or `git stash pop`, delete the cache file. It will be rebuilt on next access. A post-merge git hook can automate this.

4. **Query** — skills call a shared Python module (`scripts/sweetclaude/cache.py`) that provides query functions:

```python
from sweetclaude.cache import db

# Stories in the active epic, in sequence
stories = db.epic_stories(epic_id='EP-001', status_not=['done', 'abandoned'])

# Active epic
epic = db.active_epic()

# Backlog by priority (for go P4)
items = db.backlog(priority_order=True, exclude_done=True)

# Big-picture data
releases = db.releases_with_epics_and_stories()

# Next available ID
next_id = db.next_id(prefix='STORY')  # max existing + 1
```

### Cache miss handling

If the cache file doesn't exist when a skill queries it, rebuild automatically before returning results. Skills never fail due to missing cache — they wait for the rebuild.

## 7. go routing changes

### Priority 3 — Active epic

```
1. If mode is flow or unset → skip P3
2. Query cache: active epic (status = 'active')
   - If none → skip P3, fall through
   - If multiple → warn, use first by ID
3. Query cache: stories where epic = {active_epic.id}
     AND status NOT IN ('done', 'deferred', 'abandoned')
     ORDER BY epic_sequence
4. Propose the first result
   - "Your active epic (Workflow Engine) has {title} next in sequence."
5. If no results → EPIC_COMPLETE advisory, fall through to P4
```

### Priority 4 — Drift check

```
1. Query cache: active epic
2. If active epic exists AND proposed item's epic != active_epic.id:
   → Offer via AskUserQuestion:
     - "Move to active epic" — update story's epic field, assign next epic_sequence
     - "Work outside the epic" — proceed with orphan advisory
     - "Something else"
```

### Session state

```yaml
# .sweetclaude/state/phase.yaml (gitignored, per-developer)
active_epic: EP-001    # replaces active_milestone
```

### Fallback

If `docs/product/roadmap/epics/` does not exist:
- flow/unset: P3 already skipped — no change
- Other modes: fall back to `.sweetclaude/product/milestones/` for backward compat. Log advisory once.

## 9. Eliminated shared files

| Eliminated | Replaced by |
|---|---|
| `docs/product/backlog/INDEX.md` | Cache query: `db.backlog()` |
| `docs/product/roadmap/ROADMAP-INDEX.md` | Cache query: `db.releases_with_epics_and_stories()` |
| Epic `stories: [...]` list | Cache query: `SELECT * FROM items WHERE epic = ?` |
| Release `epics: [...]` list | Cache query: `SELECT * FROM items WHERE release = ?` |
| Story/chore/bug counters | Cache query: `db.next_id(prefix)` |

All of these become derived views from per-item files. No shared file to conflict on.

## 10. ID assignment for teams

Without a counter file, two developers creating stories simultaneously could pick the same ID. Mitigation:

1. `db.next_id('STORY')` scans all existing files (via cache) and returns `max + 1`.
2. After creating the file, the developer commits it. If another developer created the same ID, git will show a conflict on the filename — an obvious, easy-to-resolve collision.
3. This is rare for teams of 2-3 and trivially fixable when it occurs.

For larger teams, a future enhancement could use branch-prefixed IDs or a lightweight lock file. Not needed now.

## 11. Migration from current state

### New projects

No migration needed. `sweetclaude:adopt` creates the directory structure and cache from scratch.

### Existing v4 projects

1. Story files already exist in `docs/product/backlog/` with correct frontmatter — no change needed.
2. `epic` field already exists on stories — just needs to be populated when epics are created.
3. `epic_sequence` field is new — defaults to null (unsequenced) until assigned.
4. `milestone` field on stories becomes unused — can be removed or ignored.
5. INDEX.md is deleted (or gitignored) after confirming cache works.
6. Roadmap directory and entity files are created fresh.
7. Cache is built on first session start.

Migration script: read all story files, strip `milestone` field, add `epic_sequence: null` if missing. One-time, reversible.

## 14. Risk and backout

This work is on `experimental/roadmap-cache-v1`. Tagged as an experimental release (e.g., `4.1.0-experimental.1`). Not pushed until validated locally.

**Backout plan:** Delete the branch. The cache is gitignored. Roadmap files are new (no existing data lost). Story frontmatter changes (`epic_sequence` added, `milestone` removed) are the only modification to existing files — reversible by restoring from the commit before the experimental branch.

**Validation criteria before pushing:**
- [ ] Cache rebuilds correctly from existing backlog files
- [ ] `sweetclaude:go` routes from active epic in non-flow modes
- [ ] `sweetclaude:big-picture` renders epic pipeline
- [ ] Creating/closing stories works without INDEX.md
- [ ] Two developers closing different stories produces no merge conflict
- [ ] Cache invalidation after `git pull` works correctly

## 15. Open questions

1. **Completion criteria done tracking.** Where does "criterion X is done" live? Options: (a) `completion_criteria_done: [0, 2, 4]` index list in epic frontmatter, (b) separate `done: true` field per criterion (requires structured list, not string list), (c) manual tracking only via the skill. Recommend (a) — simple, per-file, no schema change to the string list.

2. **Agile sprints.** Sprint entity schema not defined here. Deferred to a separate story when agile mode is implemented.

3. **Release readiness gates.** What gates `released` status? Recommend: all epics done + manual confirmation. Deferred to `sweetclaude:deploy-ship` scope.

4. **Cache rebuild performance.** For projects with 200+ story files, how fast is the rebuild? Likely sub-second (YAML parsing is fast, SQLite inserts are fast), but should be measured. If slow, add incremental refresh based on file mtime.
